# 安心 App MVP 设计文档

## 1. 文档目的

本文档用于固化 `安心 App` 当前已确认的 MVP 设计方案，覆盖产品核心模型、入口流程、信息架构、事项创建与触发状态规则。

本文档聚焦用户端主流程与 MVP 可落地范围，不展开后台审核台、合作方系统和未来版本的复杂自动化能力。

---

## 2. 设计结论摘要

- 产品核心对象统一为 `事项`，不再使用“预案”作为主对象名称。
- App 的每日核心动作不是管理事项，而是 `主动申报自己仍然安全`。
- 每次打开 App 都先进入 `申报页`；当天第一次进入需要完整校验，当天后续再次进入只需点击申报按钮。
- App 内部主导航为：`首页 / 事项 / 我的`。
- 首页第一心智不是“任务管理”，而是“我今天仍然活着”，通过 `存活天数` 主卡表达。
- 事项分为 `线上事项` 与 `线下事项` 两类，列表按线上/线下分组。
- 所有事项都需要绑定一个触发条件，但触发条件只能二选一：`失联` 或 `死亡`，默认选 `死亡`。
- `失联 / 死亡` 的判定规则不是事项内逐条配置，而是全局统一配置，统一命名为 `触发状态`。
- `触发状态` 在创建第一个事项时顺带展示和配置，后续主要在 `我的` 中修改。
- MVP 中默认存在一套全局配置：`死亡 = 3 次未申报`。

---

## 3. 设计目标与边界

### 3.1 设计目标

- 让用户能先完成“我今天安全”的日常动作，再低频维护自己的事项安排。
- 让用户用尽可能轻的方式开始交代一件事，而不是先理解复杂系统。
- 用统一的全局 `触发状态` 减少每条事项重复配置的负担。
- 让线上与线下事项在同一产品中并存，但保持填写路径清晰。
- 保持产品气质温和、克制、鼓舞，不强化死亡或风险压迫感。

### 3.2 MVP 边界

- MVP 只实现用户端主流程。
- MVP 的完整校验方式仅支持：
  - `单纯点击`
  - `自定义密码`
- MVP 的线上事项仅支持：
  - `执行自定义脚本`
- MVP 不展示“发送特定邮件”“发送特定短信”“执行内置服务”这三类线上处理类型。
- MVP 不单独建立“文件模块”，所有材料、说明、附件都内嵌在具体事项中处理。

---

## 4. 核心对象模型

### 4.1 核心对象：事项

产品里用户实际管理的核心对象统一叫 `事项`。

事项分为两类：

- `线下事项`
- `线上事项`

每条事项至少包含以下基础信息：

- 事项类型：线上 / 线下
- 事项标题
- 触发条件：失联 / 死亡
- 事项内容主体

不同类型事项拥有不同的主体结构。

### 4.2 线下事项结构

线下事项的核心是“交代给谁、怎么处理”。

线下事项包含：

- 协助人
- 处理说明
- 事项标题
- 触发条件
- 联系方式选择
- 可选的材料 / 交代内容 / 附件

其中：

- 第一优先字段是 `协助人`
- 第二优先字段是 `处理说明`
- `事项标题` 默认由系统根据处理说明自动生成，但允许用户编辑
- 一条线下事项触发后，可以同时通过多种方式通知协助人

### 4.3 线上事项结构

线上事项的核心是“在触发后运行一段用户提交并审核通过的脚本”。

MVP 中线上事项只支持一种处理类型：

- `执行自定义脚本`

线上事项包含：

- 事项标题
- 处理类型
- 脚本代码
- 执行目标说明
- 审核说明（可选）
- 触发条件

字段优先级如下：

1. 脚本代码
2. 执行目标说明
3. 审核说明（可选）

其中：

- `事项标题` 默认根据 `执行目标说明` 自动生成
- 用户可以手动编辑标题

### 4.4 协助人结构

协助人是线下事项中的辅助对象，不是产品核心主对象。

MVP 中协助人的最小字段为：

- 姓名
- 联系方式

协助人联系方式包含以下字段，且都为可选：

- 手机号
- 邮件
- 邮寄地址

### 4.5 协助人联系方式复用与回写规则

在线下事项中指定协助人后：

- 默认可以从该协助人已有联系方式中选择
- 也允许对当前事项单独更改

事项级覆盖时采用以下规则：

- 如果协助人主档中某个联系方式字段为空，而事项中补了该字段，则允许将该值反写回协助人主档
- 如果协助人主档中该字段已有值，则事项中的改动默认只对当前事项生效，不覆盖主档

## 5. 触发状态设计

### 5.1 命名

全局的 `失联 / 死亡` 配置统一命名为 `触发状态`。

### 5.2 设计原则

- `触发状态` 为全局配置，不在每条事项内重复定义判定逻辑
- 事项本身只选择“在什么状态下触发”
- 单条事项的触发条件只能二选一：
  - `失联`
  - `死亡`
- 默认选择 `死亡`

### 5.3 MVP 默认配置

MVP 中系统默认存在一套配置：

- `死亡 = 3 次未申报`

创建第一个事项时，系统会明确展示这套默认配置，用户可以：

- 直接确认使用
- 立即修改

### 5.4 失联状态规则

首次展示触发状态时，系统先问一句：

- `是否启用失联状态`

如果用户启用 `失联`：

- MVP 不预设默认值
- 必须由用户自己输入次数
- 输入方式为自由输入
- 可输入范围：`1 - 5 次未申报`

### 5.5 死亡状态规则

死亡规则有两种成立方式：

1. 直接按未申报次数判定死亡
2. 在失联成立后，再经过设定天数判定死亡

允许不设置失联，直接设置死亡。此时只能使用：

- `多少次未申报`

如果同时启用失联和死亡，则死亡的第二段条件采用：

- `0 - 3650 天` 数字输入

默认值为：

- `0 天`

含义是：

- `0 天`：进入失联时即可同时判定为死亡
- `大于 0 天`：在失联成立后，再经过设定天数进入死亡

## 6. 入口流程设计

### 6.1 申报页定位

每次打开 App，都先进入 `申报页`。

申报页是独立入口层，不等同于 App 内部首页。

它的核心职责是：

- 让用户主动申报自己当前仍然安全
- 记录本次申报时间
- 再把用户放行进入 App 内部

### 6.2 申报规则

- 每次打开 App 都先进入申报页
- 按 `自然日` 计算
- 当天第一次进入需要走一次 `完整预设校验`
- 当天后续再次打开，只需点击申报页主按钮即可进入首页
- 每次成功申报都要更新 `最后申报时间`

### 6.3 MVP 校验方式

MVP 中完整校验仅支持：

- `单纯点击`
- `自定义密码`

未来可扩展但不进入 MVP 的方式包括：

- 手机验证码
- 手势密码
- 指纹验证
- 人脸识别
- 声音识别

---

## 7. App 内部信息架构

### 7.1 顶层结构

App 内部主导航采用三栏结构：

- `首页`
- `事项`
- `我的`

不设置面向本人用户的顶层 `执行` Tab。

原因：

- 不管是失联还是死亡，本人都不是执行阶段的主要查看者
- 顶层导航不应强化“盯执行过程”的错误心智

### 7.2 首页定位

首页采用 `混合首页`，但顶部不是申报结果摘要，而是 `存活天数` 主卡。

首页第一心智是：

- 我今天还在
- 这一天仍然值得被鼓励

`存活天数` 的定义：

- 从用户注册账号当日开始累计
- 语气采用鼓励型表达，可适当更鼓舞一些

首页结构如下：

1. 顶部主卡：`存活天数`
2. 中段：事项概况
3. 下段：下一步行动
4. 次级信息：最近一次申报时间等辅助内容

首页动作规则如下：

- 当用户已有事项时：
  - 主卡下第一优先动作为 `查看所有事项总览`
- 当用户还没有任何事项时：
  - 给两个入口：
    - `创建第一个事项`
    - `先了解怎么运作`

### 7.3 事项页定位

`事项` 页是产品核心管理页。

它负责：

- 查看全部事项
- 创建事项
- 编辑事项
- 按线上 / 线下理解事项结构

### 7.4 我的页定位

`我的` 负责账号级与全局级能力，包括：

- 账号信息
- 校验方式设置
- `触发状态` 修改
- 帮助与环境说明
- 其他账号级配置

---

## 8. 事项列表设计

### 8.1 分组方式

事项列表按以下方式分组：

- `线上事项`
- `线下事项`

不再出现“混合事项”这一层级，因为核心对象已经是单条事项。

### 8.2 触发条件角标

每条事项通过 `触发条件` 角标着色。

触发条件只有两种：

- `失联`
- `死亡`

视觉原则：

- 两者都采用低刺激、克制的表达
- 主要靠轻度色差、标签样式与文字区分
- 不使用强烈风险色制造压迫感

### 8.3 新增事项入口

事项列表页只提供一个统一入口：

- `新增事项`

点击后直接进入 `事项填写页`。

默认进入：

- `线下事项填写页`

页面内有明确类型标记，允许用户随时切换成：

- `线上事项`

切换后，表单内容同步变更。

---

## 9. 线下事项填写流程

### 9.1 填写顺序

默认新增事项先进入 `线下事项填写页`。

填写顺序如下：

1. 协助人
2. 处理说明
3. 事项标题（系统自动生成，可编辑）
4. 触发条件
5. 联系方式选择
6. 可选的材料 / 说明 / 附件

### 9.2 协助人为空时的处理

如果用户当前没有任何可选协助人：

- 不跳转独立页面
- 在当前页顶部内嵌一个 `新增协助人` 小流程

该小流程只收集：

- 姓名
- 联系方式

新增完成后，直接继续当前事项填写。

### 9.3 处理说明

`处理说明` 是线下事项的核心正文。

它的定位不是内部备注，而是触发后会发送给协助人的可执行交代内容。

后续通知方式可包括：

- 短信
- 邮件
- 邮寄

且一条线下事项允许：

- 多选同时发送

---

## 10. 线上事项填写流程

### 10.1 MVP 处理类型

线上事项的第一优先字段是 `处理类型`。

但 MVP 中对用户只显示一种处理类型：

- `执行自定义脚本`

### 10.2 填写顺序

选择 `执行自定义脚本` 后，填写顺序如下：

1. 脚本代码
2. 执行目标说明
3. 审核说明（可选）
4. 触发条件

### 10.3 执行模型

线上事项采用：

- `平台托管执行`

平台在执行脚本时，为每次执行单独准备一个沙箱环境。

沙箱约束如下：

- 仅提供对外网络
- 最长存活时间为 `5 分钟`
- 执行结束或超时后立即销毁环境

### 10.4 支持的运行时

MVP 支持：

- `Python`
- `Node.js`

### 10.5 输入与环境边界

平台不提供：

- 账号
- 密钥
- 执行参数注入

平台只保证：

- 沙箱环境本身可正常运行
- 帮助页中可查询沙箱配置与环境说明

由提交脚本的用户自行确保：

- 脚本能在该环境中正常运行

### 10.6 失败重试

脚本执行失败后：

- MVP 默认最多重试 `2 次`

## 11. 首次创建第一个事项流程

### 11.1 流程目标

首次创建的目标不是让用户一次性理解全部系统，而是尽快完成第一条事项，并在过程中顺带确认触发状态。

### 11.2 流程步骤

1. 用户点击 `创建第一个事项`
2. 进入默认的 `线下事项填写页`
3. 按线下事项顺序完成填写
4. 系统在创建过程中明确展示默认的 `触发状态`
5. 系统先默认展示：
   - `死亡 = 3 次未申报`
6. 系统提问：
   - `是否启用失联状态`
7. 用户可：
   - 直接确认默认死亡配置
   - 启用并配置失联
   - 修改死亡规则
8. 创建完成后，该事项即可绑定全局触发状态

### 11.3 设计原因

- 默认存在 `死亡 = 3 次未申报`，避免首次创建遇到完全空白的全局规则
- 首次展示时让用户明确看到并确认，避免默认配置过于隐蔽
- 把失联设计成可选展开项，避免一开始的信息负担过重

## 12. 数据流与状态关系

### 12.1 日常申报数据流

1. 用户打开 App
2. 进入申报页
3. 当天第一次进入时完成完整校验
4. 申报成功后更新最后申报时间
5. 用户进入 App 内部首页

### 12.2 事项触发关系

1. 全局 `触发状态` 负责判定当前用户进入：
   - 正常
   - 失联
   - 死亡
2. 单条事项只声明自己的触发条件：
   - 失联
   - 死亡
3. 当全局状态进入该条件时，对应事项进入触发执行

### 12.3 线下事项执行数据流

1. 事项命中触发条件
2. 系统读取该事项绑定的协助人与联系方式
3. 按事项选中的方式同时发送：
   - 短信
   - 邮件
   - 邮寄
4. 向协助人发送该事项的处理说明

### 12.4 线上事项执行数据流

1. 事项命中触发条件
2. 系统创建脚本沙箱环境
3. 注入运行时但不注入账号、密钥或参数
4. 运行脚本
5. 如失败，最多重试 `2 次`
6. 结束后销毁环境

---

## 13. 错误处理与风险控制

### 13.1 申报失败

- 当天第一次完整校验失败时，用户不能直接跳过进入 App
- 失败行为会计入未申报或失败统计，用于全局触发状态判断

### 13.2 失联配置错误

- 如果用户启用失联，但未输入 `1 - 5` 次范围内的有效值，则不能保存失联设置

### 13.3 死亡时间非法

- 如果用户同时启用失联与死亡，但死亡延迟天数不在 `0 - 3650` 范围内，则不能保存

### 13.4 线下事项缺少关键内容

- 若协助人缺失或处理说明为空，线下事项不能视为完整事项

### 13.5 线上脚本执行失败

- 记录失败结果
- 自动重试，最多 `2 次`
- 重试结束后仍失败则终止本次执行

### 13.6 主档回写保护

- 事项级联系方式只在协助人主档字段为空时才反写
- 防止临时事项改动覆盖已有稳定资料

---

## 14. 体验与视觉原则

- 整体气质保持温和、可信、鼓舞，不走高压警示风格
- 首页的“存活天数”主卡需要形成情绪记忆点
- `失联 / 死亡` 标签采用低刺激视觉，不强化恐惧
- 事项创建路径优先让用户“先开始”，再逐步补足全局规则
- 不再强调“预案系统”或“复杂容器”，统一围绕“一件事项”来理解

---

## 15. MVP 范围清单

### 15.1 必做

- 申报页
- 自然日完整校验逻辑
- 点击申报与自定义密码校验
- 首页存活天数主卡
- 事项列表（按线上/线下分组）
- 新增线下事项
- 新增线上事项
- 内嵌新增协助人
- 全局 `触发状态` 设置
- 默认 `死亡 = 3 次未申报`
- 可选启用 `失联`
- 线上脚本沙箱执行
- Python / Node.js 运行时
- 失败重试最多 `2 次`

### 15.2 暂不进入 MVP

- 验证码、手势、指纹、人脸、声音识别
- 线上事项的邮件 / 短信 / 内置服务三类处理类型
- 独立文件模块
- 面向本人用户的执行过程主导航

---

## 16. 测试与验收建议

### 16.1 用户流程验收

- 首次打开 App 时，能完成完整校验并进入首页
- 同一天再次打开时，只需点击申报按钮即可进入首页
- 首页能正确显示存活天数
- 无事项时首页能正确展示双入口
- 有事项时首页能正确跳转到事项总览

### 16.2 触发状态验收

- 默认 `死亡 = 3 次未申报` 可被正确展示和修改
- 启用失联后，只允许输入 `1 - 5`
- 同时启用失联和死亡时，死亡延迟只允许 `0 - 3650`
- 单条事项只能选择一个触发条件，且默认值为 `死亡`

### 16.3 线下事项验收

- 无协助人时，可在页内完成新增协助人
- 协助人联系方式可复用，也可事项级覆盖
- 主档空字段可被事项级数据反写
- 线下事项通知方式支持多选同时发送

### 16.4 线上事项验收

- 只能创建 `执行自定义脚本` 类型
- Python / Node.js 脚本能在沙箱中执行
- 沙箱最长 `5 分钟`
- 结束或超时后环境销毁
- 失败后最多重试 `2 次`
